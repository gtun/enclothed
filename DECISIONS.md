# Design decisions

The main choices behind enclothed, what else was considered, and why each one won. This is a condensed version of the running decision log kept during development (October to November 2026). The README covers what the app does; this file covers why it works the way it does.

## 1. Look at each photo once

**Context.** Planning outfits in a chat assistant failed for two reasons: it couldn't hold dozens of clothing photos at once, and it forgot the wardrobe when the conversation ended.

**Decision.** Intake sends a garment's photos to the model one time and stores what comes back as a structured record (category, colors, fabric, formality, warmth, and so on) plus a few sentences of styling notes. Everything after that, outfit suggestions and questions, works from the text records only.

**Why.** Text is small, cheap and permanent. An outfit request for a 90-garment wardrobe costs one text prompt, not 300 photos.

**Consequences.** Anything visual that matters for styling has to survive as text, which is why the record has a free-text `styling_notes` field written by the model. A wrong tag spoils every outfit that uses the garment, so new garments go through a field-by-field review before they're saved. The one deliberate exception is `mend`, which re-sends saved photos to fill in fields that are still blank.

## 2. Structured output instead of parsing prose

**Options considered.**

| Option | Result |
|---|---|
| Ask for JSON in the prompt and parse it | No guarantee of valid JSON or the right shape |
| A forced "fake" tool whose input schema is the model | Passed a mocked test, then the real API rejected it with a 400 for this model |
| `messages.parse(output_format=...)` with a Pydantic class | Chosen |

**Why.** The API constrains generation to the JSON Schema that Pydantic generates, and the SDK validates the reply back into the same class, running every validator. Bad output fails loudly at the boundary instead of somewhere downstream.

**Lessons.** A mocked test only checks your side of an API contract; server-side rules show up only in a real call. And the output schema, not the prompt, decides what the answer contains: the first real run returned no photo roles because the schema was still the old one.

## 3. One Pydantic model, hand-written SQL, and a drift test

**Decision.** One `Garment` class defines the data for the LLM, the database and the API. The SQLite schema is hand-written rather than generated by an ORM. Fields the model must not fill (`id`, the date added, the owner's private notes) are hidden from the schema the model sees, so it can't invent them.

**Why.** Two classes for the same garment would drift apart, and writing the SQL by hand was part of the point of the project.

**Consequences.** The class and the table have to stay in sync by hand. A test compares the model's fields against the table's columns in both directions and names the side to fix. Every row read from the database is validated through the class, so a bad row fails on read instead of producing a quietly wrong outfit.

## 4. Formality is a cap; warmth adds up

**Decision.** Formality runs 1 to 4 (casual, smart casual, business, formalwear), and a garment's rating is *the most formal occasion it can serve*. Warmth runs 1 to 5 with defined temperature bands.

**Why.** A formal piece can always be dressed down (a sport coat with worn jeans), but a casual piece can't be dressed up. So formality works as a ceiling per garment. Warmth is different: it adds up across layers, so filtering garments one at a time by warmth would wrongly drop a T-shirt that's fine under a coat. Warmth is judged per outfit, not per garment.

**Consequence.** The meaning of each level is written into the field descriptions the model reads. Without them the scales are undefined, and two reasonable ratings of the same jacket disagreed.

## 5. Rules in code, taste in the model

**Decision.** The model chooses outfits by garment ID. Code then validates every outfit against the real wardrobe before it's shown or saved: every requested anchor piece present, no duplicates, no unknown IDs, the body covered (a top and a bottom, or a one-piece), exactly one pair of shoes.

| Choice | Why |
|---|---|
| Validation returns a list of problems instead of raising | Every check runs, so an outfit with two problems reports both |
| Set operations for anchors, duplicates and unknown IDs | Set difference says exactly which IDs are missing or invented |
| Unknown IDs removed before counting categories | Otherwise validation crashes on exactly the case it exists to catch |
| Warn and log instead of retrying | A retry doubles the cost of a bad reply and may fail the same way; the log shows whether retrying is ever worth it |
| Only problem-free outfits are saved; every reply is logged | The history stays clean, and bad replies can still be found later with one `jq` query |

## 6. Outfit history: a junction table, and wears instead of counters

**Decision.** `outfits` holds each suggestion and its request; `outfit_garments` links outfits to garments, with a composite primary key `(outfit_id, garment_id)`; `wears` records each time an outfit was worn.

**Options considered.** A JSON list of garment IDs on each outfit would have worked technically, but it hides a table inside a text column: no foreign keys, no per-pairing data (whether the piece was an anchor, the styling advice), and awkward queries in the garment direction. Stored `wear_count` and `last_worn` columns on garments were dropped in favor of computing them from `wears` with one `GROUP BY`, because a stored counter is a second copy of the same fact and can drift.

**Consequence.** SQLite ignores foreign keys unless `PRAGMA foreign_keys = ON` is set on every connection, so the one connection helper sets it.

## 7. Hand-written migrations keyed on `PRAGMA user_version`

**Context.** Once real data existed, the database could no longer be deleted and recreated.

**Decision.** Numbered SQL files in `migrations/`, applied on start-up by a small runner that compares each file's number to the integer SQLite stores in `PRAGMA user_version`. `schema.sql` is always the current schema: a fresh database is created from it and stamped with the latest number, and an existing database runs only the migrations above its version.

**Why not Alembic.** One database, and building the runner was a good way to learn what migration tools do.

**Details that mattered.** Each migration runs inside an explicit `BEGIN ... COMMIT` because `executescript` ignores Python's implicit transactions; a failing migration rolls back and leaves the earlier ones committed (there's a test for this). An applied migration is never edited; mistakes are fixed forward with a new one. There are 14 migrations so far, all applied to a database holding real data.

## 8. Prompt caching, chosen from logged usage

**Context.** Every outfit request re-sent the same ~42,000-token prefix (instructions, schema, wardrobe), though only the request at the end changed.

**Decision.** The wardrobe block carries a cache breakpoint, so later requests read it from cache at a fraction of the input price. On by default, with `--no-cache` to turn it off.

**How the policy was chosen.** Measured on the real wardrobe: a cached call sent about 40 uncached input tokens instead of about 41,800, roughly a 95% input saving. The 19 logged real calls were then replayed under three policies: no cache, a 5-minute cache, and a 1-hour cache. The 5-minute cache cost about 38% less than no cache on that history; the 1-hour cache costs double on a lone call and only pays off from the third call within an hour. It ships with 5 minutes. A 1-hour cache may suit the real try-on loop (request, try it on, request again) better, and the replay can be rerun on that kind of session to decide.

## 9. Disown garments instead of deleting them

**Decision.** A garment you no longer own gets a `disowned_on` date. It disappears from suggestions but stays in the outfits it was part of. Real deletion is kept separate, for test rows and bad uploads.

**Why.** Deleting a garment would break or rewrite outfit history, and "what did I wear with that jacket I sold" is a fair question.

## 10. Ask your wardrobe: the model writes SQL, inside a sandbox

**Decision.** Questions about the wardrobe are answered by a tool-calling loop: the model gets one tool, `run_select`, writes SQL, gets the rows back, and repeats until it can answer (up to 6 turns). It answers like an inventory manager, with a number, a list, a table or garment photos, not with SQL. The conversation history is resent with each question, since the API is stateless.

**Why SQL instead of fixed filter tools.** The questions people ask ("what's my color spread", "which jackets have never been in an outfit") are open-ended, and SQL covers them without a new tool per question.

**Guardrails.** Model-written SQL is treated as untrusted:

- It runs against a throwaway, in-memory copy of only the signed-in person's rows, with private notes removed.
- The copy is locked with `PRAGMA query_only` and a SQLite authorizer that allows reads only.
- Every query has a 2-second time limit and a result-size fuse; when the fuse trips, the model is told to select fewer columns or aggregate.
- There's no row cap on purpose: the model is expected to write queries that return only what it needs, and the size fuse catches the ones that don't.

## 11. Sign-in through Cloudflare Access, with no fallback user

**Decision.** People sign in with a one-time code emailed by Cloudflare Access. The app verifies the signed token Cloudflare adds to every request, then looks up the user by email. Each person has their own wardrobe; admins can switch into another person's wardrobe, with a banner showing whose they're viewing.

**Why.** Passwords and account recovery are a lot of code to get right for a few invited users. Verifying a signed token is a small, well-defined job.

**Rule.** Any failure to verify is an error, never a fallback to a default user. A local-only setting signs in as the first user for development, and it must never be set on a server.

## 12. Workflow: one branch per change, required CI

**Decision.** Every change goes on its own branch and merges into `main` as one squashed commit through a pull request. GitHub Actions runs the import check and the full pytest suite, and a ruleset blocks merging until it passes. Releases are tagged with semantic versions (`v1.0.0` on October 29).

**Why.** Two early merges reached `main` broken (a stale test, then a missing colon that broke every command). The required check stopped that class of problem.

**What CI can't catch.** Tests that disappear. CI stayed green when a test file was overwritten and the count dropped from 106 to 75, and again when a test file was misnamed so pytest skipped it. The routine now includes knowing the expected test count for a change and checking `git diff --staged --stat` before committing.

## Things that went wrong

A selection, newest first. Each one changed how the code or the routine works.

| Date | What happened | Cause | What changed |
|---|---|---|---|
| Oct 30 | A debug log line would have raised `AttributeError` on every real call, with or without `-v` | A field rename didn't reach the log call, and logging arguments are evaluated before the level check | Search for the old name after any rename |
| Oct 30 | CI green while the test count fell from 106 to 75 | A new test file was pasted over an existing one | Know the expected test count; recovered the file with `git show` and `git restore --source` |
| Oct 29 | `WHERE id IN (:ids)` with `'58,59'` matched nothing | One placeholder binds one value, not a list | `executemany`, plus a `rowcount` check that rolls the transaction back |
| Oct 25 | The coverage check flagged every valid one-piece outfit (caught in review) | `not (A) or B` negates only A | Parenthesized the whole condition; tests now cover it |
| Oct 22 | Nearly every outfit suggested something to buy | The response format had a "Missing" slot, and a slot invites filling | The field now means a purchase only when the wardrobe can't meet the request |
| Oct 21 | The first real outfit reply was cut off | Thinking tokens count toward `max_tokens` | Raised the cap and logged what the reply actually contained |
| Oct 18 | A mocked test passed; the real call returned 400 | The API doesn't allow forced tool choice for this model | Switched to structured output (decision 2) |
| Oct 18 | Tagging returned no photo roles | The output schema was still the old class | The schema decides what the answer contains, not the prompt |
